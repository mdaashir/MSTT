# Development

## Prerequisites

| Tool | Version | Why |
| --- | --- | --- |
| Node.js | 20+ (22 LTS recommended) | Both packages declare `engines.node >= 20` |
| Docker | optional | Only needed for the containerised stack |
| uv | optional | Only needed for the Python smoke tool |

`better-sqlite3` is a native module and it ships `binding.gyp` **without** an
`install` script. That means npm treats it as a gyp package and runs
`node-gyp rebuild` during `npm ci` — on every platform, not just musl. The build
needs a C/C++ toolchain and Python:

| Platform | How it is satisfied |
| --- | --- |
| Docker | `apk add python3 make g++` in the API image's build stage |
| GitHub Actions | `sudo apt-get install python3 make g++` in the backend job |
| Windows | Visual Studio Build Tools + Python (node-gyp finds it automatically) |
| macOS | Xcode command line tools (already present with Node) |

If `npm ci` fails with `gyp ERR! find Python`, that is the missing piece — not the
code, and not the lockfile. `npm install` masks it by reusing an already-built
binary, which is why the two commands can disagree.

## First run

```bash
# API
cd backend
npm install --include=dev
npm run dev            # http://localhost:3000

# UI (second terminal)
cd frontend
npm install --include=dev
npm run dev            # http://localhost:5173
```

> `--include=dev` matters: if `npm config get omit` returns `dev`, a plain
> `npm install` silently skips TypeScript, ESLint and Vitest.

The database file is created automatically on first boot, so no setup step is
required. `npm run seed` in `backend/` adds five sample tickets (it skips if any
exist).

## Scripts

Both packages expose the same four commands:

| Command | What it does |
| --- | --- |
| `npm run dev` | Watch mode (API: tsx, UI: Vite) |
| `npm run build` | Type-check and produce `dist/` |
| `npm run typecheck` | Types only, no emit |
| `npm test` | Vitest |
| `npm run lint` | ESLint, zero warnings tolerated |
| `npm run format` | Prettier write |

Backend extras: `npm start` (run the built output) and `npm run seed`.

## Environment

`backend/.env.example` lists everything. Every value has a typed default in
`src/config.ts`, so the API runs with no `.env` at all.

| Variable | Default | Meaning |
| --- | --- | --- |
| `PORT` | `3000` | HTTP port |
| `DATABASE_PATH` | `data/tickets.db` | Relative to `backend/`, or `:memory:` |
| `CORS_ORIGIN` | `http://localhost:5173` | Allowed browser origin |
| `NODE_ENV` | `development` | Affects logging only |
| `API_PROXY_TARGET` | `http://localhost:3000` | UI only: where Vite proxies `/api` |
| `VITE_SITE_URL` | `http://localhost:5173` | UI only: absolute origin for canonical/OG/sitemap URLs |

`VITE_SITE_URL` matters for SEO and is easy to forget: canonical links, Open
Graph tags and the generated `sitemap.xml` must contain absolute URLs. If it is
unset in a production build, those files will point at `localhost` and every
shared link will preview the wrong host. Set it to the real deployment origin:

```bash
VITE_SITE_URL=https://tickets.example.com npm run build
```

## SEO

The UI ships the things crawlers and link previews need:

| Asset | Where it comes from |
| --- | --- |
| Title, description, keywords, robots | `frontend/index.html` |
| Canonical, Open Graph, Twitter card | `frontend/index.html`, with `__SITE_URL__` replaced at build time |
| `robots.txt` | Generated by `frontend/seo.ts`; disallows `/api/` |
| `sitemap.xml` | Generated by `frontend/seo.ts` from the same origin |
| Favicon, social image | `frontend/public/` |

`seo.ts` is a small Vite plugin: it rewrites the placeholder tokens, emits
`robots.txt` and `sitemap.xml` during `build`, and serves the same bytes from
middleware in `dev`, so both can be checked at `http://localhost:5173/robots.txt`
before anything is deployed. Generating them beats committing them, because the
origin lives in one place instead of three files that drift apart.

## Continuous integration

`.github/workflows/ci.yml` runs on every push to `main` and every pull request
targeting it. Both packages are checked in parallel, so a backend failure never
hides a frontend one:

| Job | Steps |
| --- | --- |
| Backend | toolchain, `npm ci`, typecheck, lint, test, build |
| Frontend | `npm ci`, typecheck, lint, test, build |

Each job caches npm on its own lockfile, and a superseded run on the same ref is
cancelled rather than paid for twice.

The backend job installs `python3 make g++` **before** `npm ci` for the reason
above. Dropping that step is the single most likely way to "break CI" here.

To run exactly what CI runs, from either package:

```bash
npm ci --include=dev && npm run typecheck && npm run lint && npm test && npm run build
```

Validate the workflow itself before pushing changes to it:

```bash
docker run --rm -v "$PWD:/repo" -w /repo rhysd/actionlint:latest
```

## Testing

```bash
cd backend && npm test        # 34 API tests, supertest + in-memory SQLite
cd frontend && npm test       # 16 unit tests, error mapping and client wiring
```

The API tests build the app through `createApp(deps)` against a fresh in-memory
database, so they exercise the same wiring production uses.

## Before opening a PR

```bash
# in both packages
npm run typecheck && npm run lint && npm test && npm run build
```

Plus, if the API contract changed, run the smoke tool against a live server:

```bash
cd tools/smoke && uv run python smoke.py
```

## Known sharp edges

- **The UI production build type-checks test files.** `npm run build` runs
  `tsc -b`, which includes everything in `tsconfig.json`. Tests are part of the
  type surface on purpose; they have caught real regressions.
- **`noUncheckedIndexedAccess` is on.** Array indexing yields `T | undefined`.
  This is why test helpers that index into mock calls assert instead of casting.
- **Search wildcards are literal.** `q` is not escaped, so `%` matches nothing
  special; the worst case is a broader match, never an injection, because the
  value is always bound as a parameter.
