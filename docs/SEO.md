# SEO and discoverability

Two separate surfaces, and they need different work:

1. **The web app** — metadata for search engines and link previews.
2. **The GitHub repo** — description, topics and README keywords, which drive
   discovery in GitHub search and the repo's own search result.

---

## The web app

### What ships

| Asset | Source | Notes |
| --- | --- | --- |
| `<title>` | `frontend/index.html` | "Support Ticket Tracker — Track and Resolve Support Tickets" |
| `<meta name="description">` | `frontend/index.html` | ~150 characters, mentions priority and status |
| `<link rel="canonical">` | `frontend/index.html` | Absolute, built from `VITE_SITE_URL` |
| Open Graph | `frontend/index.html` | `og:title`, `og:description`, `og:url`, `og:image`, dimensions |
| Twitter card | `frontend/index.html` | `summary_large_image` |
| `robots.txt` | generated by `frontend/seo.ts` | Allows `/`, disallows `/api/` |
| `sitemap.xml` | generated by `frontend/seo.ts` | One URL, `lastmod` set at build time |
| Favicon | `frontend/public/favicon.svg` | |
| Social image | `frontend/public/og-image.svg` | 1200×630 |

### The one thing you must set

`VITE_SITE_URL` is the absolute origin used for canonical, Open Graph and sitemap
URLs. Those **must** be absolute, so there is no sensible way to infer them.

```bash
VITE_SITE_URL=https://tickets.example.com npm run build
```

In Docker it is a build arg:

```bash
docker build -t ticket-tracker-web --build-arg VITE_SITE_URL=https://tickets.example.com ./frontend
```

**If you forget it**, the build still succeeds and every URL points at
`http://localhost:8080`. That is deliberate: a build that visibly points at
localhost is easier to catch than one that silently points at a plausible but
wrong domain. It is the first thing to check if a link preview looks wrong.

### Why generate robots.txt and sitemap.xml

They are emitted by a small Vite plugin rather than committed as static files:

- the origin lives in **one** place instead of three files that drift apart
- the sitemap `lastmod` is the build date, not a hand-edited string
- the plugin also serves both from middleware in `dev`, so
  `http://localhost:5173/robots.txt` can be checked before deploying

If client-side routing is added later, list the real paths in
`frontend/seo.ts`. A sitemap full of URLs that 404 does more harm than good.

### Verifying

```bash
# development
curl http://localhost:5173/robots.txt
curl http://localhost:5173/sitemap.xml

# built output
grep -E 'canonical|og:url' frontend/dist/index.html    # must show the real origin
grep -c '__SITE_URL__' frontend/dist/index.html        # must be 0
```

Then check the deployed page with a link-preview debugger (Facebook Sharing
Debugger, Twitter Card Validator) since those cache aggressively.

### Honest limitations

- **The app is a single page.** SEO gains are bounded: one canonical URL, one
  sitemap entry. Anything more would require real routes and prerendering.
- **`og-image.svg` is SVG.** Major crawlers accept it, but some older Slack and
  Facebook unfurlers only render raster. Rasterise to `og-image.png` if previews
  matter, and update the two `og:image` tags.
- **Content is client-rendered.** Google executes JS; many other crawlers and
  most unfurlers do not. The `<head>` metadata is the part that reliably works,
  which is why it carries the real title and description.
- **This is an internal tool.** If it should not appear in search at all, change
  `<meta name="robots" content="index, follow">` to `noindex, nofollow` and drop
  the sitemap. That is a one-line decision, not a refactor.

## The GitHub repo

GitHub search weighs the description, topics and README, so those carry the
discoverability weight.

```bash
gh repo edit mdaashir/MSTT \
  --description "Full-stack support ticket tracker: React + Vite UI, Express + TypeScript REST API, SQLite, Docker, and GitHub Actions CI." \
  --add-topic support-tickets,issue-tracker,helpdesk,react,typescript,express,sqlite,docker,vite,github-actions,rest-api,full-stack
```

| Field | Value |
| --- | --- |
| Description | Names the domain (support ticket tracker) and the whole stack |
| Topics | 12, covering domain, language, framework and infra |
| README | Opens with what it is and who it is for, then features, then a stack list |

The README's first paragraph matters most: it is what GitHub and Google show in
results. It leads with "full-stack support ticket tracker", not with the project
codename.
